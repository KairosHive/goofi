# Bug hunt 2026-10-01

Twenty Opus reviewers read the repository by partition for real defects; a second agent tried to
refute each finding against its callers and guards. What survived is listed here, one bullet per
defect, as remaining work. Nothing here was changed in the code.

Reviewed 16 findings; 14 confirmed.

## goofi-core

- **A second reduction states its own input length as orig_len and drops the upstream reduced map**
  (`backend/goofi-core/src/reduce.rs:37`, drift, severity low). 1) graphics:Ramp at
  width=height=4096 feeds signal:GraphicsIn with size=1024. GraphicsIn emits a 1024x1024x4 f32 frame
  with meta.reduced = {"0":{orig_len:4096},"1":{orig_len:4096}}, built with origin_of plus
  note_reduced. 2) A browser viewer subscribes to GraphicsIn's `out` and declares a 256 box, or
  declares nothing, which gives undeclared_axes. 3) The bridge reducer decodes the frame. At
  reducer.rs:628 it calls reduce_for_view with axes on dim 0 and dim 1. Each axis records
  axis_record(1024), and set_reduced replaces the map with
  {"0":{orig_len:1024},"1":{orig_len:1024}}. If the plan shrinks only dim 0, the dim-1 entry is also
  lost. 4) The frontend's originShape and reconstructMeta then report the node's shape as 1024x1024
  (or 1024 on an unshrunk dim) instead of 4096x4096. If the frame carries channel coords, orig_coord
  holds the already-subsampled coords, not the originals. Fix: In reduce_for_view, start `reduced`
  from the frame's existing reduced map (`match frame.meta().reduced() { Some(MetaValue::Map(m)) =>
  m.clone(), _ => BTreeMap::new() }`). For each axis it shrinks, keep the existing entry if that dim
  already has one, because its orig_len and orig_coord describe the true origin. Write
  axis_record(orig_len) plus the verbatim coords only when the dim has no earlier entry, the same
  rule as origin_of. Keep the `reduced.is_empty()` early return tied to whether this call shrank
  anything, for example with a separate `shrunk` flag, so a frame that needs no new cut is still
  returned unchanged.

- **Sidecar meta delta never records that a key was cleared, so a reader keeps the stale value**
  (`backend/goofi-core/src/lib.rs:849`, drift, severity low). 1. Record the output slot of a node
  that passes its input meta through, such as a math node fed by an EEG source with sfreq=250 and
  labelled channels. The first sidecar line has meta {"sfreq":250,"channels":{...},"index":0}, and
  `said` now holds sfreq and channels. 2. While recording, rewire the node's input to a source that
  has no sfreq and no channel labels, such as a constant. The output frames now have sfreq=Null and
  empty channels. 3. Recorder::write_queued routes them to the same Array stream, because takes()
  matches on Kind only. Beside::line calls write_meta_delta, which skips both keys (`matches!(value,
  Null) || !in_json(value)`) and writes only index. 4. A reader that carries keys forward, as the
  format documents, reads every later frame as sfreq=250 with the old channel names. If the original
  source is wired back later, nothing is written because `said` still matches. That is consistent
  only because the clear was never recorded. Fix: In write_meta_delta, when a key held in `said` is
  now Null or not representable in JSON (and is not META_TIME), write `"key":null` once and remove
  the key from `said`. A key that is not in `said` and is Null still writes nothing. Update the
  format doc on write_meta_delta and Beside to say that null means unset, and extend the recording
  situation in goofi-tests with a frame where meta is cleared mid-stream.

## goofi-bridge ops

- **A refused patch load stops the running recording and announces nothing** (`backend/goofi-
  bridge/src/ops/session.rs:192`, drift, severity medium). 1. Arm an output and run `record start`.
  Every client now has record.running=true, and the status beat re-sends `record_changed` every
  period while `recorder.running()` is true. 2. Run `session load --path /nonexistent.gfi`, or
  `--content` with a manifest that does not parse. 3. load_patch calls recorder.stop(). It returns
  Ok(Some(folder)): the take is finalized and running() becomes false. No event is sent. 4.
  stage_load fails (or load_doc fails, then rescan to the live mount), and the op returns Err. The
  open patch is unchanged. 5. No GraphReplaced is sent. The beat sees running()==false and sends
  nothing. So the RecorderPanel and the TopBar record dot on every client show a running recording
  with frozen elapsed time and streams. This lasts until a later `record start`/`record stop` or a
  reconnect snapshot. If the user then runs `record stop`, it fails with "no recording runs". The
  recording also ended even though the patch was never replaced, which goes against the "a refused
  load leaves the open patch untouched" comment. Fix: Keep the stop off the graph lock, because the
  capture drain needs the graph. Broadcast whenever the stop actually ended a recording: match
  `state.recorder.stop()`. On `Ok(Some(_))`, send `super::record::record_changed(state)`. On
  `Err(e)`, keep the current send with the error attached. On `Ok(None)`, send nothing. Optionally,
  also run the stop after `stage_load` succeeds so that a missing or unreadable path does not end
  the recording. load_doc can still refuse after that point, so the broadcast is still needed.

- **A `session save` that runs at the same time as a load gives the newly loaded patch the old
  patch's file as its home** (`backend/goofi-bridge/src/ops/session.rs:180`, race, severity medium).
  1. Patch A is open with home a.gfi, and its workspace is large (for example, recordings), so the
  zip takes seconds. 2. Client 1 (the CLI or an agent harness) runs `session save` with no path, or
  with `--path a.gfi`. Save::run reads mount M_A and revision r under the graph lock, drops the lock
  and starts save_archive. 3. Client 2 (a browser on its own socket) runs `session load b.gfi`.
  load_patch stages off the lock, then commits under the graph lock: the mount becomes M_B,
  save_path becomes b.gfi, SavePathChanged(b.gfi) is sent, and M_A goes to a reclaim worker. 4.
  Client 1's zip finishes. Under the graph lock, version != r (in the usual case), so the dirty flag
  stays as it is. The guard is then dropped, and line 180 sets save_path = a.gfi and sends
  SavePathChanged(a.gfi). 5. Patch B is open, but its home is a.gfi, and every client shows a.gfi.
  The next plain save (`session save` with no path, or Ctrl+S) writes B's contents over a.gfi, and
  the patch A that was just saved is lost. Also, the reclaim worker can delete M_A while it is being
  zipped, so the save fails or packs only part of the workspace. Fix: Adopt the outcome under the
  same graph guard, and only while the patch that was packed is still the open one. Before line
  171's decision, compare `state.mount()` with the `mount` that was sampled. Each load mints a fresh
  Mount, so the path identifies the patch, and this check is stronger than the version check. If the
  mount is the same, apply the version-gated dirty or baseline update and set save_path and send
  SavePathChanged, all before the guard drops. If the mount changed, return the written path, but
  leave the session's home, baseline and dirty flag alone. Also keep the old mount alive while the
  pack runs (hold a lease on the Mount, or defer reclaim until the save finishes), so a load cannot
  delete the directory being zipped.

## goofi-bridge reducer+presence+autosave+patchfile+record

- **Slot reducer can block indefinitely on a held serve whose tick passes between the pace check and
  the next wait** (`backend/goofi-bridge/src/reducer.rs:446`, race, severity medium). 1. A viewer
  watches a slot whose producer emits one frame and then goes quiet (a constant or one-shot output).
  The WATCH_GRACE window has passed, and no snapshot was asked. 2. A pass ends with nothing owed,
  and the loop blocks. Either the producer rings with its frame, or a joiner or declare rings a poke
  and bumps `gen`. The frame or ring arrives a few microseconds before the next grid tick T. 3. The
  loop wakes, drains the frame, and sets `pending`. At the bottom check, `now_b < T`, so `pace.due`
  arms T and the loop continues without serving. 4. Back at the top, `now_t >= T`. `pace.due`
  returns the same T, because T + interval/2 is still in the future. `.filter(|at| *at > now_t)`
  drops it, no other duty is set, and the loop calls `blocking_wait_all`. The same thing happens
  when 0 < T - now_t < 1 µs, because the timeout is cut to a zero timeval, which blocks forever. 5.
  The producer does not ring again, so the frame is never broadcast. The viewer shows nothing or a
  stale frame until something else rings the door: another join, a declare, a graph settle, or a new
  frame. With a ~16 ms interval this happens rarely, but nothing recovers from it in a bounded time.
  Fix: Keep the owed duty when it is already due instead of filtering it out. For example, at line
  446 use `owed.then(|| pace.due(interval, now))` and choose the wait from the result: when `at <=
  now + 1µs`, skip the wait or call `try_wait_all`, and otherwise call `timed_wait_all`. A simpler
  option is to set the minimum timeout to 1 µs,
  `at.saturating_duration_since(now).max(Duration::from_micros(1))`. This fixes both the passed-tick
  case and the zero-timeval case. Apply the same 1 µs minimum to the grace and snapshot duties,
  which go through the same `timed_wait_all`.

## goofi-bridge term+plugins+mcp

- **Service::kill can never join the stdin writer or the stdout listener, so every kill waits out
  the full 2 s and leaves the threads running** (`backend/goofi-bridge/src/plugins.rs:355`, leak,
  severity medium). 1. Load a plugin package that has a Python service. `Service::spawn` adopts the
  stdin worker, and `listen` adopts the stdout listener. 2. Shut down. `Plugins::stop` sends the
  "stop" request, then calls `service.kill()`. 3. `child.stop(2s)` ends Python. The listener reads
  EOF and calls `service.kill()` from its own thread at the same moment. 4. One of the two
  `scope.close(2s)` calls takes the worker list and calls `join_within` on 'goofi-plugin-stdin'.
  That thread is blocked in `for message in messages`, and `Service.input` still holds the Sender,
  so the join returns None only after the full 2 s. 5. The stdin thread stays detached and listed in
  `session status` while the Service lives, which for a loaded package is until AppState drops. When
  it does drop, `Drop for Service` calls `kill()` again with `input` still alive, which costs about
  2 s more. Result: shutdown costs about 2 s per plugin service in the stop phase, plus about 2 s
  more per service at drop. The scope's promise to join its threads is broken. Every `request()`
  timeout and every failed `on_start` (line 539) blocks the caller for 2 s in the same way, and
  leaves a stdin thread behind until the process exits. Fix: Make `kill()` close the input channel
  before the join. Store the Sender as `Mutex<Option<mpsc::Sender<Value>>>`, have `write` and
  `request` lock it and send, and have `kill` take it (set it to None) before `scope.close`. The
  listener and the call workers must not keep their own long-lived Sender clones: give them a handle
  to the shared slot (for example, the `Arc<Service>` the listener already holds) so that taking the
  slot drops every Sender. When `kill` runs on the listener thread, skip joining the current thread.
  One way is to compare `std::thread::current().id()` with each worker's id. Another is to let the
  listener only drain `pending` and leave `close` to `Plugins::stop` or `Drop`.

## goofi-codec

- **A crafted `channels` key in frame meta panics or forces a huge allocation in parse_channels**
  (`backend/goofi-codec/src/lib.rs:677`, panic, severity low). 1. Encode any valid GOOF v2 frame,
  for example a string frame. Its meta is a msgpack map {"channels": {"dim18446744073709551615":
  ["a"]}}. 2. Write it into a recording data file, or publish it on a node's output service. 3. On
  read, goofi_codec::frame_meta (recorder or record reader) or goofi_codec::decode (runtime inbox,
  bridge reducer) calls split_frame (passes), then parse_meta, then parse_channels. That parses dim
  = usize::MAX and calls Axes::with(usize::MAX, ..). In debug, `dim + 1` panics with an overflow. In
  release, `dim + 1` wraps to 0, resize(0) does nothing, and `self.0[usize::MAX]` panics on the
  index. With "dim4000000000", resize tries to allocate and fill about 4e9 Axis values, and the
  process aborts on allocation failure or the OOM killer stops it. Neither case returns the Err that
  the codec's hostile-frame contract promises, and the abort cannot be caught. Fix: Bound the dim
  before calling Axes::with. Array rank is a u8 on the wire, so a dim of 256 or more can never label
  a real axis. Put the rule in one owner so both decoders agree. For example, add a goofi_core
  helper such as `Axes::with_checked(dim, axis) -> Option<Axes>` or a MAX_RANK constant of 256.
  parse_channels uses it and returns Err from parse_meta for an out-of-range dim. goofi-pymod's
  dict_to_axes uses it too and raises a Python ValueError. Add a case to the hostile-frame block in
  codec_golden.rs: a frame whose channels key is "dim18446744073709551615" must decode to Err.

## goofi-record

- **A failed write lane drops every later frame of that stream for the rest of the take, even after
  a re-arm, and does not count them** (`backend/goofi-record/src/writer.rs:150`, correctness,
  severity medium). 1) Start a take. Arm a signal output X. 2) A write fails once for X. Examples:
  ENOSPC or EIO from Stream::write or Stream::create in open_now, or frame::read refusing a frame.
  The lane calls close_now(X, "the frame could not be written: ...") and sets failed=true. 3) The
  disk recovers, or the user frees space. The user disarms X and re-arms it, or the node is reborn.
  The drain closes X ("disarmed" or "reborn") and opens a new Feed with the same StreamId. 4) Every
  later frame of X goes into the same lane, and try_send returns Ok. take_frame returns true, so the
  drain counts it as written. The lane drops it, never calls write_queued, and so never opens a
  file. 5) Until stop, X has no file, no manifest entry and no dropped count. The manifest shows
  only the first entry's closed_because. Status shows X as not open, with no loss. Fix: Make lane
  death visible to the lane's owner and end it when the stream is closed on purpose. One option:
  Recorder::close (the disarm/reborn path) removes the lane for that id from Writer.lanes after its
  flush, so the next frame starts a new lane (Writer gets a `forget(id)` that drops the sender and
  joins the thread). Also, while `failed` is set, make the lane count each discarded frame as
  dropped. Or make Writer::take return false for a dead lane, so the frames show as lost and do not
  look written.

## goofi-build+goofi-init

- **Cross-process race on the shared cargo target: one build can place another source's library
  under its key** (`backend/goofi-build/src/lib.rs:155`, race, severity low). 1. Two processes share
  one build base, e.g. two concurrent `cargo test -p goofi-tests` runs on the shared checkout (both
  use GOOFI_BUILD_DIR=<target>/goofi-build), or an e2e fleet, or goofi-bridge build.rs running
  beside a test run. 2. Process A builds Twice.rs with bytes "3.0" (key KA, crate goofi_node_twice).
  Process B builds Twice.rs with bytes "2.0" (key KB, same crate name) and blocks on cargo's target
  lock. 3. A's cargo exits and releases the lock. B's cargo takes the lock: its unit is fresh, or it
  compiles quickly, and it re-uplifts target/release/libgoofi_node_twice.so to B's library before
  A's thread (descheduled under load) runs std::fs::read on that path. 4. A reads B's bytes and
  place() writes them to out/KA/Twice.so. 5. From then on, every process that computes KA for the
  "3.0" source finds the artifact, and open() accepts it (same version+SDK hash). The node runs the
  "2.0" code and nothing reports it, until the build dir is removed. Fix: Make the uplifted output
  unique per key by putting a key prefix in the crate name, e.g. `format!("goofi_node_{}_{}",
  stem.to_lowercase(), &key[..12])`. The artifact under out/<key>/<stem>.so keeps its name, and the
  exported symbols are fixed by cdylib!, so nothing else changes. goofi-init's three-day target
  sweep removes the extra uplifted files. An alternative is a cross-process file lock on base/target
  held from before cargo starts until place() returns.

## audio engine

- **Ring swaps queued for a node are never cleared on remove, so a re-inserted uid adopts dead
  rings** (`backend/audio/goofi-audio/src/lib.rs:744`, drift, severity medium). 1. Node N (uid U)
  has an Array input. A frame larger than INBOX_SEED arrives. `room()` sets `wanted = need*4` and
  asks for a replan. 2. A settle runs `fit_rings`, which mints an inbox ring of need*4. It puts the
  producer in `swaps[U]` and sends `Msg::Rings`. 3. N is deleted by a script, MCP or test op within
  about 10 ms, before its control half ticks again. `remove` stops the half, and the half exits its
  loop without a tick. The audio side retires the slot and the consumer ends of the rings.
  `swaps[U]` stays and holds the producer. 4. The delete is undone, so U is inserted again with
  fresh SEED rings, and the minted/wanted cells are back at SEED. 5. The new half's first tick takes
  `swaps[U]` and replaces its fresh inbox producer with the stale one, before any wired frame
  arrives. 6. Frames of the same size now fit the stale capacity, so no resize is ever asked. They
  go into a ring that nothing reads. The audio side reads the fresh SEED ring, which stays empty.
  When the stale ring is full, every write fails silently. N's array input stays silent until the
  frame size changes enough to force a re-mint. Any output that was grown and is at width 1 after
  the undo also keeps a dead tap or rec consumer. If U is never inserted again, the rings leak until
  the engine shuts down. Fix: In `AudioEngine::remove`, inside the `if let Some(inst)` branch after
  `inst.control.stop()`, call `self.audio.swaps.lock().remove(&uid);`. The halt is raised and
  nothing mints for U again until the next insert, so the entry cannot come back for the dead half.
  A tick already running on the old half could still take a `Swap` minted for the new instance. To
  close that path as well, key the entry by (uid, serial) and give the half its serial in `Birth`.

- **A frame's sfreq from outside sizes an inbox ring with no upper bound, so a tiny sfreq can abort
  the process** (`backend/audio/goofi-audio/src/control.rs:521`, panic, severity medium). 1. Build a
  patch: Buffer (1000 samples) -> Meta with sfreq = 0.01 -> an audio node's Array input (playback
  waveform), with the clock at 48 kHz. 2. A frame arrives. step = 0.01/48000 ≈ 2.1e-7, so n ≈ 4.8e9
  and need ≈ 4.8e9 floats. The frame does not fit, so room() stores wanted ≈ 1.9e10 floats and the
  frame is held as pending. 3. At the next settle, fit_rings calls RingBuffer::new(1.9e10), which is
  about 77 GB, and Frames::new reserves four Vecs of the same capacity. 4. The allocation fails and
  Rust calls handle_alloc_error, which aborts the whole goofi process. If overcommit lets the
  allocation through, re-entering the pending frame touches 4.8e9 floats, and the OOM killer ends
  the process. At a larger sfreq the product need*4 can also overflow usize, and a debug build then
  panics on the control thread. Fix: In Inbox::enter, after computing step and n, refuse a frame
  whose resampled length n (or n*c) is above a fixed ceiling, for example a few seconds at the clock
  rate. Return None, and set `refused` in arrive so the node shows an error such as "a frame of T
  samples at sf Hz lasts too long to play". Use checked_mul for need*4 in room(), so the stored
  `wanted` can never overflow.

## graphics engine

- **Runtime.presenting never drops the entry of a closed window** (`backend/graphics/goofi-
  graphics/src/runtime.rs:425`, leak, severity low). 1. A patch has a Window node with a UI
  attached. It renders on the timer clock, and the UI thread is slow enough that a present job is
  still drawing when the next tick's readback arrives. 2. In that tick, `take()` calls `present()`.
  The frame is stored in `cell.pending`, and because `posted` is still true there is no new post. 3.
  The same batch deletes the Window node. `Cmd::Remove` resets the plan, and `follow_windows`
  removes the uid from `windows` and posts `close_window(id)`. 4. The job clears `posted`. No stage
  has that window any more, so nothing calls `present()` for the id again. 5.
  `Runtime.presenting[id]` keeps the `Arc<Present>` and its waiting frame (for example, 1920×1080×4
  ≈ 8 MB) for the rest of the engine's life. Each new Window node gets a new id, so every add/delete
  cycle leaks at least one map entry and sometimes one full frame. The growth has no bound in a long
  session. Resizing a window does not leak, because the id stays the same. Fix: In
  `Runtime::set_plan`, after the new plan is assigned, keep only the entries that a stage still
  uses: collect the ids from `plan.stages[i].window` into a set and call
  `self.presenting.retain(|id, _| live.contains(id))`. Also call `self.presenting.clear()` in
  `Runtime::clear`. When an entry is dropped, its waiting `Vec` is freed, and that is enough,
  because the stage that owns that spare ring is gone or no longer presents. A job that is still in
  flight holds its own Arc clone, so retain does not race with it.

## goofi-runtime+goofi-supervisor

- **Hosted node stop kills the child with zero grace, right after its Stop reply and before it can
  release its iceoryx2 ports** (`backend/goofi-runtime/src/hosted.rs:78`, leak, severity medium). 1.
  Place a Rust signal node built after boot, so it runs hosted. It ticks once, which spawns `goofi
  host serve` with a Served exchange under goofi_host_<pid>_<n>. 2. Remove the node.
  Hosted::call(Entry::Stop) sends Stop, and the child calls served.answer(seq, done). 3. The
  parent's ask returns at once, and child.stop(ZERO) runs. It closes the liveness pipe, sends
  SIGTERM to the group (default action, no handler in `goofi host`), and sends SIGKILL after a zero-
  length poll. 4. The child is still dropping Served and the library (it is at serve's return,
  before process::exit), so it dies first. 5. Its iceoryx2 node directory and the three services'
  static and dynamic configs and shm segments stay under the session root. Dead-node cleanup is off
  and nothing else removes them before Session::release. Every remove, reload or rebuild cycle leaks
  one more set for the life of the session. Fix: Let the child exit by itself before any signal:
  after a successful Stop reply, call child.wait_within(STOP_TIMEOUT). It keeps the liveness pipe
  open, sends no SIGTERM, and kills only at the deadline. If ask fails, fall back to
  child.stop(Duration::ZERO). The suggested child.stop(STOP_TIMEOUT) is not enough, because stop
  closes the liveness pipe (the child's watcher then calls process::exit(0)) and sends SIGTERM
  (default action terminates) before the grace starts, so the teardown is still cut short. Apply the
  same change in goofi-python/src/subproc.rs:92.

## frontend crdt+stores+api

- **A page reload loses this actor's undo/redo labels: the first hello is treated as a fresh session
  and history().reset() overwrites the labels it carried**
  (`frontend/src/lib/stores/graph.svelte.ts:321`, drift, severity medium). 1) In a tab, add a node.
  The manager keeps an undo entry for actor A, and the reply sets Undo to enabled with its label. 2)
  Reload the tab. sessionStorage keeps actor A, and the socket opens /control?actor=A. 3) The bridge
  sends a hello with history {undo:'Add node', redo:null} and the same instance_id as before. 4)
  _onMessage adopts those labels (or drops them if HistoryStore is not built yet). Then GraphStore
  sees _lastInstanceId === null, treats the hello as a new session, and calls history().reset(). 5)
  Undo stays disabled with no label (canUndo false) while the manager still holds the step for A.
  This lasts until the next write reply sends the labels again. Fix: In GraphStore._handle('hello'),
  after _onWholesaleLoad, adopt the hello's history labels when present: if (ev.payload.history)
  history().adopt(ev.payload.history). Also add history to the hello payload type. Another option is
  to reset history only when the instance_id changes from a known non-null id. Either way, add a
  Playwright check: make an edit, reload, and expect Undo to be enabled with its label.
